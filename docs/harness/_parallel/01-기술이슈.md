# 01-트렌드분석 조각 — LLM/기술 이슈 축

> 이 문서는 `01-trend-analyst`의 **병렬 조각 모드** 산출물이다. 지정된 축(LLM/기술 이슈)만 다루며, `docs/harness/01-trend-analysis.md`(취합본)와 검증 로그는 이 호출에서 작성하지 않는다. 취합 단계에서 다른 축(시장·사회 동향 / 경쟁 서비스 / 규제·법 / 도메인 운영규칙) 조각과 합쳐진다.

## 0. 조사 범위와 조사 시점
- 대상: PDF → HWPX 변환기(개인용, 배포 형태 미정) 구현에 실제 쓸 수 있는 기술/오픈소스 현황
  1. PDF 파싱(텍스트 추출 vs 레이아웃 보존) 라이브러리
  2. HWPX 생성/쓰기 라이브러리 유무
  3. 스캔본(이미지 기반) PDF용 OCR, 특히 한글 인식 기술 동향
  4. 생성형 AI/LLM을 문서 변환·레이아웃 복원에 쓰는 최근 사례 (규칙 J 관련 시사)
- 조사 방법: 웹 검색(WebSearch) 및 일부 웹페이지 직접 확인(WebFetch), 2026-09-27 기준.
- 이 조각은 "이 도구가 존재한다/이런 접근이 있다"는 정보 제공까지이며, 실제 채택 여부·아키텍처 결정은 2단계 기획에서 판단할 사안이다.

## 1. PDF 파싱: 텍스트 추출 vs 레이아웃 보존

| 라이브러리 | 성격 | 비고 | 출처 |
|---|---|---|---|
| PyMuPDF (fitz) | 고속 텍스트/구조 추출, MuPDF 엔진 기반 | 순수 Python 대안보다 10~50배 빠르다는 비교 존재(확인 필요 — 벤치마크 원출처 미확인) | [PyMuPDF Layout Tutorial](https://artifex.com/blog/pymupdf-layout-tutorial), [pdfplumber vs PyMuPDF vs PyPDF2](https://subhajitbhar.com/blog/pdf-extraction/pdfplumber-vs-pymupdf-pypdf2/) |
| pymupdf4llm / PyMuPDF Layout | 휴리스틱 + 머신러닝을 결합해 문서 요소(제목/표/이미지 등)를 탐지, markdown/JSON 출력 | 2025년 이후 `pip install pymupdf4llm`만으로 Layout 기능이 자동 활성화되도록 변경됐다는 설명 확인 | [PyMuPDF Layout Blog](https://pymupdf.io/blog/pymupdf-layout-tutorial) |
| pdfplumber | pdfminer.six 기반, 문자/단어/표 좌표 단위로 상세 정보 제공, MIT 라이선스 | 표 추출에 강점, 대용량 처리엔 상대적으로 느림 | [pdfplumber GitHub](https://github.com/jsvine/pdfplumber), [PyPI](https://pypi.org/project/pdfplumber/) |
| pdf2docx | PDF → DOCX 레이아웃 보존 변환(문단/이미지/표를 규칙 기반으로 파싱해 재구성) | 원저장소(ArtifexSoftware)는 유지보수가 활발하지 않다는 언급이 있고 커뮤니티 포크(sailfish009 등) 존재. 라이선스 상세는 확인 필요 | [ArtifexSoftware/pdf2docx](https://github.com/ArtifexSoftware/pdf2docx) |

**시사점**: "PDF 파싱 → 중간 구조(문단/표/이미지 좌표) → 타깃 포맷 라이터" 파이프라인은 pdf2docx가 PDF→DOCX에서 이미 검증한 패턴이며, PDF→HWPX에도 동일한 구조(파서 + HWPX 라이터)를 적용하는 것이 기술적으로 합리적이다. 단, "완전한 레이아웃 보존"과 "텍스트만 추출"은 난이도 차이가 크므로 2단계 기획에서 변환 품질 목표(예: 서식/표/이미지 위치까지 보존할지, 텍스트 재조판만 할지)를 REQ 단위로 명확히 분리할 필요가 있다.

**확인 필요**: PDF의 문자 좌표를 HWPX 문단/표 구조로 직접 매핑하는 기존 오픈소스 사례(즉 "PDF→HWPX 변환기"를 표방하는 완성도 있는 오픈소스 프로젝트)는 이번 조사에서 명확히 찾지 못했다. 검색된 것은 대부분 "HWP/HWPX ↔ 다른 포맷" 변환기(마크다운/DOCX/HTML 대상)이거나 웹 기반 상용/무료 변환 서비스였다 (경쟁 서비스 축 참고).

## 2. HWPX 생성/쓰기 라이브러리 현황

- **HWPX 포맷 자체의 개방성**: HWPX는 OWPML(Open Word-processor Markup Language) 표준을 따르는 ZIP+XML 포맷이며, OWPML은 2011-12-30 제정된 국가표준(KS X 6101)이다. 한글과컴퓨터가 HWP 5.0/HWPML 스펙을 공개한 이력이 있다. (출처: [한컴테크 - HWPX 포맷 구조](https://tech.hancom.com/hwpxformat/), [한컴 다운로드센터 - HWP·OWPML 공개](https://www.hancom.com/support/downloadCenter/hwpOwpml), 나무위키 HWP 문서 — 2차 출처 포함이므로 국가표준 제정일 등 핵심 수치는 가능하면 TTA/KS 공식 문서로 재확인 권장)
- **Java**:
  - `neolord0/hwpxlib` — OWPML 공개 스펙을 참고해 개발된 Java 라이브러리, Apache-2.0, HWPX 읽기/쓰기 지원. ([GitHub](https://github.com/neolord0/hwpxlib))
  - `neolord0/hwpxlib_ext` — 암호화된 HWPX 파일 등 확장 기능. ([GitHub](https://github.com/neolord0/hwpxlib_ext))
  - `neolord0/hwplib`(구버전 HWP 5.0용), `neolord0/hwp2hwpx`(HWP→HWPX 변환) — 같은 개발자가 유지하는 관련 프로젝트군. ([GitHub](https://github.com/neolord0/hwplib), [GitHub](https://github.com/neolord0/hwp2hwpx))
- **Python**:
  - `python-hwpx` (PyPI, Apache-2.0, Python ≥3.10) — 한컴오피스 설치 없이 순수 Python으로 HWPX를 열고(`HwpxDocument.open()`) 문단/제목 등을 추가해 새로 생성·저장 가능하다고 설명됨. ([PyPI](https://pypi.org/project/python-hwpx/6.4.0/))
  - 그 외 `hwpforge`(Rust 라이브러리를 감싼 Python 바인딩, HWPX 쓰기 전용), `hwpx-agent`, `hwp-hwpx-parser`(파싱 전용, Java 불필요), `pyhwpxlib` 등이 PyPI에 존재. ([libraries.io - hwpforge/pyhwpxlib 등 검색 결과](https://libraries.io/pypi/pyhwpxlib))
  - **확인 필요**: `pyhwpx`(이름이 유사한 별개 패키지)는 한컴오피스를 실제 설치한 뒤 COM 자동화로 제어하는 방식일 가능성이 있어 보이며, 순수 파일 생성 라이브러리인 `python-hwpx`와 혼동하지 않아야 한다 — 정확한 동작 방식은 PyPI 페이지를 더 깊이 확인해야 한다.
  - **확인 필요**: 위 라이브러리들의 실제 성숙도(단순 텍스트/문단 수준 지원인지, 표·이미지·복잡 레이아웃까지 안정적으로 지원하는지, 최근 커밋/이슈 활동)는 이번 조사에서 README·PyPI 설명 수준만 확인했고 소스코드·이슈트래커 심층 검토는 하지 못했다.

**시사점**: "HWPX를 프로그램적으로 생성/쓰기할 수 있는 오픈소스 라이브러리가 존재하는가?"라는 질문에는 **"존재한다"**고 답할 수 있다(HWPX가 공개 표준 기반 ZIP+XML이라는 근본 이유 때문). 다만 성숙도·완성도 차이가 커서, 2단계 설계에서 "직접 OWPML XML을 작성하는 자체 라이터를 만들지" vs "기존 라이브러리(hwpxlib/python-hwpx 등)를 채택할지"를 REQ/기술결정 사항으로 명시해야 한다.

## 3. 스캔본(이미지 기반) PDF의 OCR — 특히 한글 인식 동향

- **Naver Clova OCR**: 한국어 인식 정확도 97~99% 수준이라는 비교 서술이 확인됨. 다만 출처가 OCR 비교/마케팅 성격의 2차 사이트([Lido - 클로바 OCR 대안](https://www.lido.app/kr/clova-ocr-daean), 2026)여서, 1차 벤치마크 데이터가 아니라는 점을 감안해야 한다("확인 필요" — 정확한 수치는 네이버 공식 벤치마크로 재확인 권장). 다국어 혼재 문서·저품질 스캔에서는 정확도가 90% 미만으로 떨어지는 사례도 언급됨.
- **Tesseract OCR**: 한국어(`kor`) 언어팩이 존재하는 오픈소스 OCR 엔진. CPU 기반 처리로 상대적으로 느리다는 비교(분당 약 25페이지)가 있으나, 이 수치의 1차 출처는 확인하지 못했다("확인 필요"). ([Tesseract Wikipedia](https://en.wikipedia.org/wiki/Tesseract_(software)))
- **PaddleOCR**: PP-OCRv5/PaddleOCR-VL이 100개 이상 언어를 지원한다고 공식 문서에 명시되어 있고 한국어도 포함된다. 다만 GitHub 공식 저장소의 실제 논의([Discussion #15371](https://github.com/PaddlePaddle/PaddleOCR/discussions/15371))를 직접 확인한 결과, PP-OCRv5 출시 초기에는 한국어 인식 모델이 없었고("it do NOT support Korean") 이후 약 2개월 뒤 `korean_PP-OCRv5_mobile_rec` 모델이 추가되며 지원이 시작된 것으로 확인된다. 즉 한국어 지원은 **비교적 최근에 추가된 기능**이라 실사용 정확도 검증 사례가 아직 많지 않을 수 있다.
- **EasyOCR**: 한국어 지원 언어 목록에 포함된다고 알려져 있으나, 이번 조사에서 구체적 정확도 수치는 확인하지 못했다 ("확인 필요").
- **OCR-프리 접근 — NAVER Clova AI `Donut`**: 이미지에서 별도 OCR 단계 없이 바로 구조화된 정보를 생성하는 Document Understanding Transformer(Swin Transformer 인코더 + BART 디코더), ECCV 2022 논문, 오픈소스(clovaai/donut, Apache-2.0 계열). 한국 기업(Naver)이 만든 오픈소스라는 점에서 한글 문서 처리에 참고할 만하다. ([GitHub](https://github.com/clovaai/donut), [논문](https://arxiv.org/pdf/2111.15664))

**시사점**: 스캔본 PDF를 지원할지 여부, 그리고 OCR 엔진을 (a) 완전 로컬 오픈소스(Tesseract/PaddleOCR/EasyOCR/Donut 계열)로 할지 (b) 클라우드 API(Naver Clova OCR, 아래 4번의 Upstage 등)로 할지는 "개인용/로컬 동작"이라는 프로젝트 성격과 직결되는 핵심 기획 결정이다. 로컬 오픈소스 OCR은 비용·프라이버시(문서가 외부로 안 나감) 면에서 유리하지만, 한국어 인식 정확도는 클라우드 상용 서비스 대비 낮거나(특히 저품질 스캔) 검증 사례가 적을 수 있다는 트레이드오프가 있다.

## 4. 생성형 AI/LLM을 문서 변환·레이아웃 복원에 쓰는 사례 (ORCHESTRATOR.md 규칙 J 관련)

**결론부터: 실제로 존재하는 흐름이다.** 확인된 사례:

- **Upstage Document Parse** (한국 스타트업 Upstage) — 단순 OCR을 넘어 문서 레이아웃/구조를 이해하는 AI로, 자체 설명상 "Vision Language Model(VLM)"을 활용해 표 구조 인식(TSR), 레이아웃 요소 탐지(LED)까지 수행하고 HTML/Markdown으로 출력한다. 한글·한자 인식을 지원하며 정확도 95% 이상을 표방한다(자사 제공 수치, 확인 필요). 클라우드 API 형태로 제공된다. ([Upstage Document Parse](https://www.upstage.ai/ko/products/document-parse), [Upstage OCR API 문서](https://console.upstage.ai/docs/capabilities/document-digitization/document-ocr))
- **LlamaParse** (LlamaIndex) — GPT-4.1, Gemini 2.5/3.1 Pro 등 파운데이션 모델(LLM/LVM)을 백엔드로 PDF를 LLM 친화적 구조로 파싱하는 클라우드 서비스. ([LlamaIndex - Best LLM Document Parsers 2025](https://www.llamaindex.ai/insights/best-llm-document-parser-2025))
- **Docling(IBM 오픈소스) / Granite Docling 258M** — 로컬 실행이 가능한 경량 모델로 레이아웃 보존형 문서 이해를 수행. ([CodeCut - Docling vs Marker vs LlamaParse](https://codecut.ai/docling-vs-marker-vs-llamaparse/))
- **Marker-PDF** — 신경망 기반 레이아웃 탐지에 `--use_llm` 옵션으로 LLM 정제(clean-up) 패스를 결합할 수 있는 오픈소스 도구.
- **범용 비전 LLM(GPT-4V/Claude/Gemini 등)을 직접 OCR·레이아웃 인식에 사용하는 접근** — 최신 모델일수록 문서 QA/OCR 격차가 줄었다는 평가가 있으나, 레이아웃이 복잡하거나 스캔 품질이 낮을 때 "존재하지 않는 표 셀·축 레이블을 지어내는" 헐루시네이션 사례가 여전히 보고된다. ([futureagi.com - Visual Language Models 2026](https://futureagi.com/blog/visual-language-models-2025/), [parsli.co - LLM OCR vs Traditional OCR 2026 벤치마크](https://parsli.co/blog/llm-ocr-vs-traditional-ocr))

**이 프로젝트에 대한 시사점 (규칙 J 관련 — 정보 제공까지, 채택 여부는 기획 단계 결정 사항)**:
1. 만약 이 PDF→HWPX 변환기가 (스캔본 레이아웃 복원, 표 구조 보정, 손상된 레이아웃 재구성 등의 목적으로) LLM/VLM을 내부에 포함시키기로 한다면, 이는 "서비스 자체에 생성형 AI 기능이 포함된 경우"에 해당할 수 있어 ORCHESTRATOR.md **규칙 J**의 적용 대상이 될 수 있다.
2. 그 경우 2단계 기획에서 최소 아래를 확인해 정식 REQ-ID로 등록해야 한다(이 조사에서는 선택지 제시까지만 함):
   - **사용자 입력(PDF 원문)이 LLM에 어떻게 전달되는가**: 위 Upstage/LlamaParse처럼 클라우드 API로 문서 전체 또는 페이지 이미지가 외부 서버로 전송되는 구조인지, Docling의 소형 모델이나 Donut처럼 로컬에서 완전히 처리되는 구조인지에 따라 "개인 PDF 문서(계약서, 신분 정보가 포함된 서식 등일 수 있음)가 제3자 서버로 나가는지 여부"가 결정된다.
   - **LLM에 외부 도구/함수 호출 권한을 주는지**: 단순 텍스트/레이아웃 생성 용도로만 쓰는지, 파일 시스템 접근 등 추가 도구 권한을 주는 에이전트형 구조인지.
   - **생성 결과를 그대로 사용자에게(또는 HWPX 파일에) 노출하는지**: 레이아웃 복원 결과에 환각이 섞여 원문 왜곡이 발생할 수 있으므로, 결과를 검증 없이 그대로 최종 HWPX에 반영할지 여부.
3. 반대로, LLM/VLM 없이 규칙 기반 파싱(PyMuPDF + python-hwpx/hwpxlib 조합 등)과 전통적 OCR(Tesseract/PaddleOCR)만으로 구현한다면 규칙 J의 적용 대상이 아닐 가능성이 높다 — 이 자체가 2단계에서 내려야 할 핵심 아키텍처 결정이다.

## 5. 패키지 환각 방지 — 실제 존재 확인 여부

## 6. 타 축 참고 (다른 조사 축에 넘기는 단서)

- **경쟁 서비스 축**: `letpang.com`(HWPX 변환 웹툴), `polarisofficetools.com`(HWP/HWPX→PDF), `sysmetrix/To-Hwpx`(브라우저 기반 Markdown/DOCX/HTML→HWPX 변환기) 등 이미 존재하는 유사 변환 서비스가 다수 확인됨 — 경쟁 환경 비교 축에서 다뤄야 함.
- **규제/정책 축**: 개인용 PDF에는 주민등록번호, 계약 내용 등 개인정보가 포함될 수 있다. 만약 위 4번의 LLM/OCR 클라우드 API(Naver Clova, Upstage 등)를 채택하면 사용자 문서가 외부 서버로 전송되는 구조가 되므로, 국내 개인정보보호법 관점의 이슈로 이어질 수 있다는 단서를 규제 축에 전달한다.
- **시장/사회 동향 축**: 해당 없음(이 축에서 발견된 특별한 시장 동향 단서 없음).
- **도메인 운영규칙 축**: 해당 없음("영업일/마감시간" 같은 운영 규칙이 PDF→HWPX 변환이라는 기술 도메인에는 해당하지 않는 것으로 보임 — 도메인 운영규칙 담당 축에서 별도 확인 필요).

## 7. 확인 필요 목록 (요약)

- HWPX 국가표준(OWPML/KS X 6101) 제정일 등 핵심 사실은 2차 출처(한컴테크 블로그, 나무위키)로만 확인함 — 가능하면 TTA/국가표준 공식 문서로 재확인 필요.
- `python-hwpx`, `hwpxlib` 등 HWPX 라이터들의 실제 표/이미지/복잡 서식 지원 성숙도 — README 수준만 확인, 실사용 검증 필요.
- `pyhwpx`가 한컴오피스 COM 자동화 방식인지 순수 파일 생성 방식인지 — 이름이 유사한 다른 패키지(`python-hwpx`)와 혼동 주의, 재확인 필요.
- Naver Clova OCR 97~99%, Tesseract 분당 25페이지 등 구체 수치의 1차 출처 미확인.
- EasyOCR의 한국어 인식 정확도 수치 미확인.
- PaddleOCR 한국어 모델(`korean_PP-OCRv5_mobile_rec`)의 실사용 정확도 벤치마크 미확인(최근 추가된 기능이라 사례 부족 가능성).
- `hwpforge`, `hwpx-agent`, `hwp-hwpx-parser`, `hwpkit`, `hwpx2` 등 소규모 오픈소스 프로젝트의 유지보수 활성도(최근 커밋, 이슈 대응) 미확인.
- pdf2docx의 정확한 현재 라이선스(원본 vs 포크 간 차이) 미확인.
