## 0. 입력 재확인 및 v2 대비 변경 범위 요약

### 0-1. 03단계(v5) 산출물 재확인 — 화면 설계에 쓸 데이터/계약 전량 확인

- **라우트(03 §4-4)**: `GET /`(업로드 폼+진행률 영역+후원/개인정보처리방침 링크), `POST /convert`(202+`job_id` 또는 413/429/503), `GET /api/jobs/<uuid:job_id>/`(JSON: `status`/`progress`/`warnings`/`errors`, 404), `GET /download/<uuid:job_id>/`(200 파일streaming / 422 콘텐츠실패 또는 인프라실패 / 409 진행중 / 404 없음·만료), `GET /healthz`, `GET /privacy/`. **관리자 라우트(Django admin)는 이 표에 없다 — 04 범위 밖(§1-4).**
- **`ConversionJob` 모델(03 §3-2)**: `job_id`(UUID), `status`(pending/processing/done/failed/expired), `created_at`/`started_at`/`finished_at`/`downloaded_at`/`purged_at`, `enable_ocr`/`ocr_lang`, `progress_stage`/`progress_current_page`/`progress_total_pages`/`progress_message`, `result_success`/`result_warnings`/`result_errors`. **원본 파일명·클라이언트 IP 필드는 스키마에 아예 없다(DEC-036) — 화면이 이를 요구하면 즉시 정합성 위반이므로, 파일명 복원은 전량 클라이언트(JS) 책임으로 설계한다(§1-3).**
- **DONE/FAILED 구분 규칙(03 §3-2 상태전이 주석, 반드시 화면 설계에 반영)**: `DONE`은 라이브러리가 통제된 방식으로 마쳤다는 뜻이지 성공의 동의어가 아니다(`result_success=False`일 수 있고 이 경우 `result_errors`는 **사용자에게 노출 가능한** 콘텐츠 문제). `FAILED`는 executor 자신의 인프라 레벨 실패로, 이 경우 사용자에게는 **내부 원인을 노출하지 않는 일반 메시지**만 보여준다. 이 구분을 화면 카피 설계의 최우선 원칙으로 삼는다(§2 Panel C).
- **예외 계층 7종(03 §4-2, v4/v5 동일, 변경 없음)**: `EncryptedPdfError`/`CorruptedPdfError`/`EmptyPdfError`/`OutputPathError`/`ContainerBuildError`/`TesseractNotFoundError`/`INTERNAL_ERROR`(캐치올). **이 7종은 `DONE+result_success=False`의 `result_errors`로 노출되는 실패 종류다** — 웹 컨텍스트에서 일부(특히 `OutputPathError`)는 사용자가 유발할 수 없는 조건으로 바뀌므로 04단계가 문구를 재해석한다(§2 Panel C, §7).
- **비기능 수치(03 §5, DEC-029/030 확정치 — 예시가 아니라 확정치)**: 업로드 파일 크기 상한 **50MB**, 변환 소프트 타임아웃 **5분**, 동시 변환 처리 **최대 2건**+대기열 **20건** 초과 시 503, TTL **60분**, 레이트리밋 **IP당 시간당 20회 + 동시 진행중 2건**, 콜드스타트(Render 무료 플랜 스핀다운) 지연 가능.
- **보안/개인정보(03 §6)**: 완전 익명(로그인 없음, DEC-023), `job_id`(UUID)가 사실상의 capability token(§6-1) — 이 값을 아는 사람만 진행률 조회·다운로드 가능. 국외이전 고지 무조건 필요(DEC-035, §2-3). 관리자 화면은 Django 표준 admin, 04 범위 밖(§6-1, §8-2-3).
- **04단계 인수인계 7개 항목(03 §8-2)**: 본 문서 서두의 "필수 반영 사항"으로 그대로 승계 — 각 항목이 어느 절에서 해소됐는지 아래 0-2에 매핑한다.

## 1. 핵심 사용자 플로우

### 1-1. 전체 구조 — v2 대비 무엇이 바뀌는가

- v2는 GUI 7화면(G-1~G-7)+CLI 3종을 설계했다. v3는 **웹 화면을 사실상 1개의 단일 페이지 앱(SPA형 진행 공개, `converter/templates/converter/index.html`)** 안의 3개 패널(업로드/진행/결과) + **별도 정적 페이지 1개(개인정보처리방침)** 로 축소한다 — 03 §4-4의 실제 라우트가 `GET /`와 `GET /privacy/` 두 페이지 라우트뿐이기 때문이며(그 외는 JSON API), 화면 수를 임의로 늘리지 않는 것이 과설계 배제 원칙과도 부합한다.
- **완전 익명 다중사용자 전제(03 §8-2-1)**: 로그인·회원가입·"최근 변환 목록"·"재열기" 같은 개인화 UI는 어디에도 존재하지 않는다. 각 사용자는 자신의 브라우저 세션이 기억하는 `job_id` 하나만 알 수 있으며, 이 `job_id`가 사실상의 접근권한이다(03 §6-1). 따라서 **동시에 다른 사용자가 무엇을 변환하는지는 화면 어디에도 노출되지 않는다**(노출할 데이터 자체가 없다 — REQ-030 수집최소화와도 정합).
- **`job_id`는 URL에 반영해 새로고침·재방문 내성을 준다(권장, Could-have)**: `POST /convert` 성공 시 브라우저 URL을 `history.replaceState`로 `/?job=<job_id>` 형태로 갱신한다. 이렇게 하면 사용자가 페이지를 새로고침하거나(같은 탭) 이 URL을 북마크/공유해도 60분 이내라면 진행 상태를 다시 조회하거나 결과를 다운로드할 수 있다 — `job_id` 자체가 이미 유일한 접근권한이므로(03 §6-1) URL에 노출해도 새로운 보안 경계를 만들지 않는다. 단, **이 링크를 아는 사람은 누구나 해당 파일을 다운로드할 수 있으므로(capability token의 본질적 특성), 민감한 문서를 변환했다면 이 링크를 타인과 공유하지 말라는 안내를 진행/결과 패널에 노출한다**(§2 Panel B). 이 기능은 03 API를 확장 요구하지 않는다(기존 `job_id`만 재사용) — 05단계가 시간이 부족하면 생략 가능한 Could-have로 명시하며, 생략 시에도 같은 탭 내 새로고침 복원은 `sessionStorage`로 대체 가능하다(아래 1-3).
- **자바스크립트 필수(정직한 한계 명시)**: 업로드 즉시응답+폴링(REQ-027)·클라이언트 측 다운로드 파일명 복원(DEC-036)은 구조적으로 JS 없이는 구현할 수 없다(03이 no-JS 폴백 라우트를 설계하지 않았음 — 새 라우트를 임의로 추가하지 않는다는 원칙에 따라 04도 폴백을 만들지 않는다). `<noscript>` 태그로 "이 서비스는 자바스크립트가 필요합니다. 브라우저 설정에서 활성화해주세요."를 명시한다. 이는 WCAG AA 위반이 아니다(WCAG는 보조기술이 활성화된 상태에서의 접근성을 요구하며, "JS 없는 브라우저 지원"을 요구하지 않는다) — 단, 정직하게 한계로 기록한다(v2 §5-3의 Tkinter 접근성 한계 명시 원칙과 동일한 태도).

### 1-3. 다운로드 파일명 복원 인터랙션 (DEC-036, 03 §8-2-4 필수 반영)

> 서버는 원본 파일명을 전혀 모른다(스키마에 필드 자체가 없음, §0-1). `Content-Disposition`은 항상 범용 이름(`converted.hwpx`)만 내려준다(03 §4-4). 따라서 "원래 이름으로 저장되는 것처럼 보이는" 경험은 **전적으로 클라이언트 JS의 책임**이며, 이 로직은 03의 API 계약을 확장하지 않는다(서버는 그대로 두고 클라이언트만 다룬다).

1. 파일 선택 시점(`<input type=file>`의 `change` 이벤트)에 `file.name`(브라우저가 이미 로컬에서 알고 있는 값, 서버 전송 전)을 JS 변수 + `sessionStorage`(키: 나중에 발급될 `job_id`가 아직 없으므로 임시로 "pending"에 저장했다가, `job_id` 발급 즉시 그 키로 옮겨 저장)에 기억해둔다.
2. `POST /convert` 성공 응답으로 `job_id`를 받으면, 방금 기억해둔 원본 파일명을 `sessionStorage["job:<job_id>:filename"]`에 확정 저장한다. (같은 탭에서 새로고침해도 유지되며, 탭을 닫으면 사라진다 — 서버에 영구 저장하지 않는다는 원칙과 정합.)
3. 결과 패널에서 [다운로드] 버튼 클릭 시, `fetch('/download/<job_id>/')`로 **직접 URL 이동이 아니라 JS fetch로 바이트를 받는다**(직접 이동 시 브라우저가 서버의 `Content-Disposition` 범용 이름을 그대로 써버려 이 인터랙션 자체가 무력화되므로, 반드시 fetch 방식이어야 한다).
4. 응답을 `blob()`으로 변환하고, `URL.createObjectURL(blob)`로 임시 URL을 만든 뒤, 화면에 없는 `<a>` 엘리먼트를 동적 생성해 `href`=객체URL, **`download` 속성 = 복원한 파일명**(`sessionStorage`에서 원본 파일명을 꺼내 확장자만 `.pdf` → `.hwpx`로 치환, 원본이 `.pdf`로 끝나지 않으면 그대로 뒤에 `.hwpx`를 붙임)으로 지정 후 프로그래밍적으로 클릭, 완료 후 `URL.revokeObjectURL()`로 정리한다.
5. **저하(degradation) 경로**: `sessionStorage`에 원본 파일명이 없는 경우(예: 다른 탭에서 링크를 열었거나, 공유받은 링크로 처음 접속) — 오류로 처리하지 않고 **범용 이름(`converted.hwpx`)으로 조용히 대체**한다. 이는 결함이 아니라 의도된 정상 저하이며, 화면에는 별도 경고를 띄우지 않는다(서버가 파일명을 몰라도 핵심 기능인 "다운로드" 자체는 항상 동작해야 하므로).

### 1-4. 관리자 화면 — 04단계 범위 밖 (해당없음, 사유 명시)

03 §6-1·§8-2-3에 따라 이 서비스의 "관리자 화면"은 **Django 표준 `django.contrib.admin`을 벤더 기본 그대로 사용**한다(운영자가 `ConversionJob` 현황을 조회/수동 삭제하는 최소 ops 도구, AI-AUTO-WORK `admin_auth.py` 레이트리밋 패턴 재사용). 이 화면은 (a) 일반 이용자에게 전혀 노출되지 않고, (b) Django가 기본 제공하는 표준 UI를 그대로 쓰며 커스터마이징 요구사항이 없고, (c) 이용자 경험(UX) 설계 대상이 아니라 운영 도구이므로, **본 문서는 이 화면을 설계하지 않는다("해당없음")**. 05단계 구현자는 이 화면에 대해 04단계 산출물을 기다릴 필요가 없다.

### 1-5. CLI (운영자/개발자 전용, 참고 — 03 §4-3 변경 없음)

02 §8-3 A-15/03 §1-3(unit-11 비고)에 따라 CLI(`cli/__main__.py`)의 사용주체는 이제 **운영자/개발자**로 재해석되었다(익명 다수의 웹 이용자가 아님). 03이 CLI 명세(§4-3) 자체를 변경하지 않았으므로, **v2 §1-2/§2(C-1~C-3)에서 이미 확정한 CLI 화면 명세는 그대로 유효하며 본 리비전이 재설계하지 않는다.** 04단계의 핵심 노력은 이제 사실상 유일한 최종사용자 접점인 웹 UI(§1-2)에 집중한다(02 §4 REQ-015 Should→Must 승격 근거와 동일 논리).

### Panel D. 조회 불가 (job 없음/만료, 404 응답 공통 처리)

- **목적**: `job_id`가 존재하지 않거나(오타/공유받은 잘못된 링크) 60분 경과로 만료된 경우, 두 경우를 굳이 구분하지 않고 하나의 화면으로 안내한다(03 §4-4가 두 경우 모두 동일하게 404를 반환하도록 설계했으므로 — 서버가 구분해주지 않는 것을 클라이언트가 억지로 구분하지 않는다, §7).
- **구성 요소**: 안내 문구("요청을 찾을 수 없습니다. 60분이 지나 자동으로 삭제되었거나 잘못된 주소입니다."), [새로 업로드하기] 버튼(→ Panel A, URL도 `/`로 정리).

### W-2. 개인정보처리방침 (`GET /privacy/`, `legal/views.py`, REQ-030)

- **목적**: 03 §2-3이 확정한 국외이전 고지를 포함해, 개인정보 처리 원칙을 투명하게 고지한다.

  - 수집 항목: 업로드된 PDF 파일 내용 자체(파일명·이용자 식별정보는 수집하지 않음, DEC-036/DEC-023)

  - **국외이전 고지 5항목(03 §2-3, DEC-035, 개인정보보호법 제28조의8 대응)**: 이전되는 국가, 이전받는 자(Render/DB운영사/Cloudflare, 실제 법인명은 배포 확정 시 채움 — 자리표시자), 이전 목적, 보유·이용기간, 이전 거부 방법(거부 시 서비스 이용 불가임을 정직하게 고지)

  - 문의 채널: GitHub Issues 링크(운영자 이메일 비공개 원칙과 정합 — 익명 서비스이므로 별도 창구를 새로 만들지 않는다)

## 3. 디자인 시스템 원칙

> **기존 디자인 시스템 계승 원칙**: v2가 이미 이 프로젝트의 색상 팔레트(대비 검증 완료)를 확정해뒀다 — 이는 "이 프로젝트의 기존 디자인 시스템"에 해당하므로 색상 토큰의 **값 자체는 그대로 승계**한다. 다만 구현 매체가 Tkinter(`ttk.Style`)에서 웹(CSS)으로 바뀌므로, 매체 종속적인 부분(타이포그래피 폰트 스택, 단위, 적용 메커니즘)만 웹 표준으로 재정의한다.

### 3-1. 색상 토큰 (v2 값 그대로 승계, CSS 커스텀 프로퍼티로 구현)

| 토큰명 | 값 | 용도 | WCAG AA 대비 |
|---|---|---|---|
| `--color-bg-base` | `#FFFFFF` | 기본 배경 | — |
| `--color-bg-subtle` | `#F5F6F8` | 카드/배너 배경, 진행바 트랙 | — |

| `--color-text-secondary` | `#5A5F66` | 보조 텍스트(통계, 캡션, 상시 안내 배너) | ≈ 5.4:1 (AA 통과) |
| `--color-primary` | `#1F6FEB` | 주 액션 버튼 배경, 링크 | 흰 배경 위 텍스트로는 대비 부족 가능 → 주 버튼은 흰 글자+파랑 배경으로만 사용 |

### 3-2. 타이포그래피 (웹 표준으로 재정의 — v2의 Windows 전용 폰트 지정 폐기)

| 토큰명 | 값(CSS `font-family`) | 크기(`rem`, 기준 16px) | 용도 |
|---|---|---|---|
| `--font-heading` | `-apple-system, BlinkMacSystemFont, "Malgun Gothic", "Apple SD Gothic Neo", "Noto Sans KR", sans-serif`, weight 700 | 1.25rem | 화면 제목/배지 텍스트 |
| `--font-body` | 위와 동일, weight 400 | 1rem(=16px, 웹 최소 권장 본문 크기) | 본문, 버튼 라벨 |
| `--font-caption` | 위와 동일, weight 400 | 0.875rem | 보조 설명, 통계 캡션 |
| `--font-mono` | `"Consolas", "SFMono-Regular", Menlo, monospace` | 0.875rem | 파일 크기 등 수치 표기(있는 경우) |

- **v2 대비 변경**: v2는 Windows 전용 "맑은 고딕" pt 단위 고정을 사용했다(DEC-011 Windows 우선 배포 전제). 웹은 사용자의 OS/브라우저가 임의이므로 **시스템 폰트 스택(OS별 기본 한글 산세리프)**을 사용하고, 크기는 `rem`(브라우저 기본 폰트 크기 배율에 따라 확대/축소됨)으로 전환한다. 이는 v2 §6-3의 "OS 텍스트 크기 설정을 Tkinter가 반영 못 하는 한계"를 웹에서는 **아예 해결**한다 — 브라우저 확대(Ctrl/Cmd + `+`) 시 `rem` 단위 텍스트가 자동으로 함께 커지므로, v2가 앱 자체에 만들었던 "글자 크게" 토글(구 G-7)이 웹에서는 **불필요해진다**(WCAG 1.4.4 Resize Text는 브라우저 네이티브 확대로 충족, 별도 앱 기능 불필요 — 과설계 회피).
- 본문 최소 크기 1rem(16px) 이하로 내려가지 않는다.

### 3-3. 간격/레이아웃 그리드 (반응형 기준으로 재정의)

- 기준 단위 4px(`rem`으로 0.25rem 배수: 0.25/0.5/0.75/1/1.5/2rem).
- 콘텐츠 최대 폭 640px(가운데 정렬, 한 화면에 표시되는 정보량이 적어 넓은 데스크톱 화면에서도 텍스트 줄 길이를 과도하게 늘리지 않기 위함 — 가독성).
- 모바일(<480px)에서는 좌우 여백 16px, 데스크톱은 24px.
- **클릭/터치 타깃 최소 크기 44×44px**(v2의 32×88px에서 상향 — 데스크톱 마우스뿐 아니라 모바일 터치 입력을 고려해야 하므로, 업계 통용 터치 접근성 권장값인 44px을 최소 높이로 채택. WCAG AA 자체가 이 수치를 의무화하지는 않으나 실무 기준으로 04단계가 명시한다, v2와 동일한 논리 구조).

### 3-4. 아이콘

- 이모지 글리프 또는 인라인 SVG 아이콘 중 택1(구현 자유), 어느 쪽이든 **반드시 텍스트 라벨을 함께 표기**하고 아이콘 자체에는 `aria-hidden="true"`를 부여해 스크린리더가 아이콘을 이상하게 읽지 않고 옆의 텍스트 라벨만 읽게 한다(v2의 "유니코드 글리프+텍스트 병기" 원칙을 웹 ARIA 관례로 구체화·강화한 것).

## 5. 접근성 기준 (웹, WCAG 2.1 AA 목표)

> v2는 Tkinter의 구조적 한계(플랫폼 접근성 API 노출 부족)를 "정직한 한계+완화책"으로 다뤘다. 웹은 **네이티브 HTML 시맨틱 요소(button/input/label/fieldset)만 제대로 써도 대부분의 AA 요건이 자연스럽게 충족되는 매체**이므로, 이번 버전은 한계를 인정하는 톤이 아니라 **기준을 직접 만족시키는 톤**으로 서술한다.

### 5-1. 키보드 내비게이션 (WCAG 2.1.1/2.1.2/2.4.3)

- 모든 인터랙티브 요소는 네이티브 HTML 요소(`<button>`, `<input>`, `<a>`)로 구현해 Tab/Shift+Tab만으로 자동으로 도달 가능하게 한다(Tkinter 시절처럼 수동으로 tabindex 순서를 관리할 필요가 최소화됨 — DOM 소스 순서와 시각적 순서를 일치시키는 것만으로 충분).
- 패널 전환(A→B→C/D) 시 **포커스를 새 패널의 제목(heading)으로 프로그래밍적으로 이동**시킨다(스크린리더/키보드 사용자가 패널이 바뀐 것을 놓치지 않도록, `tabindex="-1"`+`.focus()`).
- `<a>`/`<button>`은 Enter(및 버튼은 Space)로 기본 활성화되므로 별도 구현 불필요.
- 스킵 링크("본문으로 바로가기")를 페이지 최상단에 두어 헤더 반복 탐색을 건너뛸 수 있게 한다.
- 파일 입력은 네이티브 `<input type=file>`을 시각적으로 숨기지 않는다(완전 커스텀 드롭존으로 대체 시 키보드 접근이 끊길 위험 — v2가 GUI 위젯에서 강조했던 "네이티브 우선" 원칙의 웹 버전).

### 5-2. 색 대비 (WCAG 1.4.3/1.4.11) — §3-1 참고, 값 동일

- 본문 텍스트 4.5:1 이상, 비텍스트 UI 요소(포커스 링, 입력 테두리) 3:1 이상 — §3-1 표가 실측치와 일치함(웹은 Tkinter의 OS 테마 간섭 문제가 없으므로).
- 상태는 색상 단독으로 구분하지 않고 아이콘+텍스트 병기(§3-4).

### 5-3. 스크린리더/시맨틱 구조 (WCAG 4.1.2, 1.3.1)

- 랜드마크 역할(`<header>`, `<main>`, `<footer>`) 사용, 페이지 제목(`<title>`)이 현재 패널 상태를 반영(예: "PDF→HWPX 변환 | 진행 중").
- 동적으로 갱신되는 진행률/에러 배너는 `aria-live` 영역으로 감싸 포커스를 빼앗지 않고 내용 변경을 공지한다(§4 `ProgressBar`/`InlineErrorBanner`).
- 폼 요소는 반드시 `<label for=...>` 또는 `<fieldset><legend>`로 명시적 라벨을 갖는다(placeholder만으로 라벨을 대체하지 않음).
- 이미지/아이콘에는 `alt=""` 또는 `aria-hidden="true"`(장식용) 처리, 의미 전달은 항상 인접 텍스트가 담당.

### 5-4. 기타 AA 상당 기준

- **타이밍(WCAG 2.2.1)**: 에러/경고 배너는 자동으로 사라지지 않는다(사용자가 다음 액션을 취하거나 상태가 바뀔 때까지 유지). 단, `PersistentBanner`(개인정보 안내)는 애초에 닫기 자체가 없다(§4).
- **오류 식별(WCAG 3.3.1)**: 모든 에러 상태는 무엇이 문제인지 구체적 텍스트로 설명하고 다음 행동을 제공한다(§2 각 상태표).
- **터치/클릭 타깃**: §3-3의 44×44px 최소값 적용.
- **텍스트 크기 조정(WCAG 1.4.4)**: `rem` 단위 사용으로 브라우저 200% 확대까지 레이아웃 붕괴 없이 대응(§3-2).
- **자바스크립트 필수 한계(정직한 명시)**: §1-1에서 명시한 대로 이 서비스는 JS 없이 핵심 기능(업로드/진행률/다운로드)이 동작하지 않는다. `<noscript>` 안내를 제공하되, 이를 "해결"이 아니라 "정직한 한계 고지"로 취급한다(v2가 Tkinter 한계를 다룬 것과 동일한 태도).

## 6. 반응형/디바이스 대응 기준

> v2(데스크톱 전용 Tkinter)는 "모바일 브레이크포인트 개념이 적용되지 않는다"고 명시했다. 웹 공개 서비스는 정반대다 — **어떤 기기로 접속할지 전혀 통제할 수 없으므로, 모바일 우선(mobile-first) 반응형이 필수**다.

### 6-1. 브레이크포인트

| 구간 | 폭 | 레이아웃 |
|---|---|---|
| 모바일 | < 480px | 단일 컬럼, 폼 요소 전체 폭, 좌우 여백 16px |
| 태블릿 | 480~768px | 단일 컬럼 유지(콘텐츠 최대폭 640px 이내라 테블릿부터는 폭 변화 없음), 여백만 24px로 확대 |
| 데스크톱 | > 768px | 콘텐츠 영역 가운데 정렬, 최대 폭 640px(§3-3), 여백은 뷰포트 남는 공간으로 자동 배분 |

- 모바일 파일 선택은 OS 네이티브 파일 앱/사진첩 연동에 브라우저 기본 동작을 그대로 위임한다(커스텀 파일 선택 UI를 만들지 않음, 과설계 회피).
- 경고/에러 목록처럼 항목 수가 가변적인 영역은 세로 스크롤이 자연스럽게 발생하도록 고정 높이를 주지 않는다(모바일 뷰포트 제약 대응).

### 6-2. 뷰포트/줌

- `<meta name="viewport" content="width=device-width, initial-scale=1">` 지정, 사용자 줌(pinch-zoom) 비활성화 금지(`maximum-scale` 제한 금지 — WCAG 1.4.4와 직결).

### 6-3. 네트워크 환경 대응 (웹 고유 — v2에는 없던 관점)

- 모바일 환경은 데스크톱보다 네트워크가 불안정할 수 있어, 폴링 실패(타임아웃/오프라인)를 별도로 처리한다 — 폴링 요청이 실패하면 즉시 에러로 전환하지 않고 **지수 백오프로 최대 3회 재시도** 후에도 실패하면 "네트워크 연결을 확인해주세요" 배너를 노출한다(단, `job_id` 자체는 유효하므로 네트워크가 복구되면 자동으로 폴링을 재개해 사용자가 새로 시작할 필요가 없게 한다).

### 6-4. 브라우저 호환성

- 최신 Chromium계/Safari/Firefox 최신 2개 메이저 버전을 지원 기준으로 한다(레거시 IE 등은 지원하지 않음 — `fetch`/`URL.createObjectURL` 등 §1-3의 다운로드 인터랙션이 이를 전제로 함, 이는 공개 웹 서비스의 통상적 관례이며 03이 별도로 구형 브라우저 지원을 요구하지 않았음).

## 7. 설계서(API/데이터 모델)와의 정합성 체크

> 03단계 §3(`ConversionJob`)·§4(라우트/예외)에 정의된 데이터만 화면에 사용했는지 항목별로 확인한다. **결론(먼저 제시)**: 03단계 산출물에 없는 데이터를 화면에 "요구"한 사례는 **0건**이다. 아래는 설계 과정에서 모호했던 지점들과 그 해소 방식을 투명하게 기록한다.

| 화면 요소 | 필요한 데이터/근거 | 03단계 근거 | 정합 여부 |
|---|---|---|---|
| Panel A 사전 고지(50MB/5분/3분) | 상수(REQ-029 확정치) | 03 §5 | 일치(상수, API 응답 불필요) |
| Panel A OCR 체크박스/언어 | `enable_ocr`, `ocr_lang` (POST 바디) | 03 §3-2, §4-4 | 일치 |
| Panel A 413/429/503 에러 분기 | HTTP 상태 코드만 사용, **응답 바디 내용은 파싱하지 않음** | 03 §4-4 | **일치(의도적 설계)** — 03은 이 세 에러의 JSON 바디 스키마를 정의하지 않았다. 바디 내용에 의존하는 설계를 하면 "03에 없는 데이터를 요구"하는 것이 되므로, **상태 코드만으로 분기하는 방어적 설계**를 택했다(예: 429가 "시간당 20회 초과"인지 "동시 2건 초과"인지 서버가 구분해주지 않으므로, 화면도 두 경우를 하나의 일반 문구로 통합 — §1-2 표). 향후 03/구현팀이 에러 코드 필드를 추가하면 더 구체적인 문구로 세분화할 수 있으나, v1 화면 설계는 이를 전제하지 않는다. |
| Panel B 대기열 순번 표시 | (표시하지 않음) | 03 §3-2/§4-4에 대기열 내 순번 필드 없음 | **일치(요구하지 않음)** — "대기 중"이라는 사실만 표시하고 순번은 표시하지 않도록 화면을 설계해 API 확장을 요구하지 않았다 |
| Panel B 5분 소프트타임아웃 배너 | **클라이언트 타이머**(작업 제출 시각 기준, `sessionStorage`) | 03 §4-4/§5가 "폴링 응답 생성 시 처리"라고 서술했으나 정확한 JSON 필드명은 명시하지 않음 | **일치(대안 설계로 해소)** — 애초에 클라이언트가 이미 "언제 작업을 제출했는지" 알고 있으므로, 서버가 별도 필드(예: `elapsed_seconds`)를 내려주지 않아도 클라이언트 자체 시계로 5분 경과를 판단할 수 있다. 이는 03에 없는 데이터를 요구하는 대신 **클라이언트가 이미 가진 정보로 동일한 사용자 경험을 재현**한 것이다 — 03에 새 필드를 요청할 필요가 없어 "3단계 피드백 필요" 항목으로 세지 않았다 |
| Panel B 폴링 응답 지연 배너 | (클라이언트 `fetch` 자체의 왕복시간 측정) | API 응답 불필요, 순수 클라이언트 로직 | 일치 |
| Panel C 통계 요약(총 페이지/표/이미지 수) | `ConversionStats` 상당 필드 | **03 §3-2 `ConversionJob` 모델에는 `ConversionStats`에 대응하는 필드가 없다**(v4의 `ConversionResult.warnings`/`errors`만 `result_warnings`/`result_errors`로 이관됨, 통계 필드는 이관 목록에 없음) | **불일치 가능성 발견 → 화면 요구 축소로 해소(임의 확대 아님)**: 본 문서는 통계 요약 UI를 "있으면 표시, 없으면 생략"하는 **선택적(Should-have) 컴포넌트**로 낮췄다(§2 Panel C 표의 각주). `ConversionJob`에 통계 필드가 없는 이상 이를 필수 요소로 요구하면 규칙 위반이므로, 필수 요소에서 제외하는 방향으로 화면 요구 자체를 축소했다 — **05단계 구현자가 통계를 보여주고 싶다면 03/`ConversionJob` 스키마에 필드 추가를 먼저 요청해야 하며, 04단계가 이를 기정사실인 것처럼 설계하지 않는다.** |
| Panel C 완전성공/부분성공/콘텐츠문제 분기 | `status`, `result_success`, `result_warnings`, `result_errors` | 03 §3-2 상태전이 주석 | 일치 |
| Panel C 처리실패(FAILED) 일반 문구 | `status=failed`만 사용, `result_errors` 내용에 의존하지 않음 | 03 §3-2("이 경우 비어있을 수 있다") | 일치(의도적 방어 설계) |
| Panel C 다운로드(§1-3) | `GET /download/<job_id>/`, 클라이언트 `sessionStorage`(원본 파일명) | 03 §4-4, DEC-036 | 일치 — 원본 파일명은 서버 데이터가 아니라 **명시적으로 클라이언트 전용 데이터**임을 DEC-036이 확정했으므로, 클라이언트 상태로 다루는 것이 오히려 설계 의도와 정확히 일치한다 |
| Panel D 조회 불가 | 폴링/다운로드 404 | 03 §4-4 | 일치. **없음과 만료를 구분하지 않는 것도 정합** — 03이 두 경우를 동일한 404로 응답하도록 설계했으므로, 클라이언트가 이를 억지로 구분하는 UI를 만드는 것이 오히려 "서버가 주지 않은 구분 정보를 있는 것처럼 요구"하는 결함이 된다 |
| W-2 개인정보처리방침 5항목 | 정적 콘텐츠(상수) | 03 §2-3 | 일치 |
| 푸터 후원/GitHub/라이선스 | 정적 상수(SPONSOR_URL 등, 자리표시자) | 03 §8-3 승계, DEC-006/012/015 | 일치 — 별도 About 페이지/라우트를 새로 만들지 않고 기존 라우트(`/`)의 푸터에 통합해 03의 라우트 표를 확장하지 않았다 |

**최종 집계**: "03단계에 없는 데이터를 화면에 요구"한 사례 **0건**. "3단계 피드백 필요"로 전환한 질문 **0건**(2건의 잠재적 공백 — 에러 바디 스키마 미정, 소프트타임아웃 필드 미정 — 은 모두 화면 설계 축소 또는 클라이언트 자체 로직으로 해소했으며, 이 해소 과정 자체를 투명하게 위 표에 기록해 추후 심사자가 "왜 이렇게 설계했는지" 추적 가능하게 했다). 03 §8-3 미해결 사항 5건 중 어느 것도 이번 화면 설계를 막지 않는다(03이 이미 "착수 가능" 등급으로 분류함).
