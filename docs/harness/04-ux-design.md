- 작성 에이전트: 04-ux-designer

## 0. 03단계 산출물 재확인 (설계 착수 전 스캔)

- 03 §4-1 `convert()`/`ConversionOptions`/`ProgressEvent`/`ConversionResult`/`ConversionStats`/`ConversionWarning` — 화면에 뿌릴 수 있는 필드 전량 확인 완료.
- 03 §4-2 예외 계층(7종: `EncryptedPdfError`, `CorruptedPdfError`, `EmptyPdfError`, `ContainerBuildError`, `OutputPathError`, `TesseractNotFoundError`, 그리고 계층 밖 `INTERNAL_ERROR` 캐치올) + 엣지케이스 8종(암호화 PDF, 손상 PDF, 0페이지, 출력 파일 충돌, 출력 권한 없음, OCR 엔진 없음, 수식 판정 불가, 대용량 PDF) 전량 확인 완료 — 이 8종을 §1·§2에서 빠짐없이 화면 상태로 매핑한다.
- 03 §4-3 CLI 명세(`convert`/`batch`, 종료코드 0/1/2), §4-4 GUI 이벤트 계약(스레드 분리, `queue.Queue` 폴링, 취소 버튼 없음, 후원 버튼) 확인 완료.
- 03 §6-2 개인정보 원칙(로그에 파일명 대신 일련번호, `settings.json`에 "최근 목록 지우기" 기능 권고) — 04단계가 화면으로 구현해야 할 항목으로 확인.
- 03 §8-3 미해결 사항: (1) 라이선스 MIT — 해소됨(About 화면에 표기), (2) 후원 URL — GitHub Sponsors 플랫폼은 확정(DEC-015), 실제 URL은 05단계 unit-18에서 확정 예정(자리표시자로 설계), (3) HWPX 지원 버전 번호 — 05/06단계 실측 예정(자리표시자로 설계). **이 두 자리표시자는 03단계가 이미 "확인 필요/추후 확정"으로 명시해둔 항목이므로, 04단계가 새로 만든 미해결 질문이 아니다** — 그대로 승계해 화면에 `{PLACEHOLDER}` 형태로 명시한다.

## 1. 핵심 사용자 플로우

### 1-1. GUI 플로우 (P1~P4 페르소나 공통, REQ-015)

```
[G-1 메인 화면: 빈 상태]
   │  "찾아보기" 클릭 → OS 파일 선택 다이얼로그(filter: *.pdf)
   ▼
[G-1 메인 화면: 파일 선택됨]
   │  - 입력 경로 표시, 출력 경로 자동 생성(입력파일명.hwpx, 같은 폴더)
   │  - 출력 경로가 이미 존재 → 인라인 경고 배지 노출 + "덮어쓰기" 체크박스 활성화(사전 감지, §1-1-a 참고)
   │  - OCR 사용 체크박스(기본 OFF) → 체크 시 언어 체크박스(한국어 기본 ON/영어 OFF) 노출
   │  - [변환 시작] 버튼 활성화(입력 경로 존재 시에만)
   ▼ [변환 시작] 클릭
[G-2 진행 화면] ── 워커 스레드가 orchestrator.convert() 호출, UI 스레드는 큐 폴링으로 갱신
   │  - stage별 진행바 갱신: loading → extracting → building → saving → done
   │  - loading 단계 message에 대용량 경고 문구가 포함되면 배너로 별도 강조 표시(엣지케이스: 대용량 PDF)
   │  - 창 닫기(X) 시도 시 확인 다이얼로그("변환이 진행 중입니다. 종료하시겠습니까?") — 취소 버튼은 없지만 강제 종료 경로는 확인을 거친다
   ▼ convert() 반환
   ├─[success=True, warnings=[]] ──────────────→ [G-3 결과 화면: 완전 성공]
   ├─[success=True, warnings=[...]] ───────────→ [G-3 결과 화면: 부분 성공(품질 리포트)]
   └─[success=False, errors=[...]] ────────────→ [G-4 오류 다이얼로그] (엣지케이스: 암호화/손상/0페이지/출력충돌/권한없음/OCR엔진없음 6종 + 예외 계층에만 있던 ContainerBuildError까지 매핑, §2 G-4 표 참고)
        │ [확인] 또는 [다른 이름으로 저장]/[다른 폴더 선택] 클릭
        ▼
      [G-1 메인 화면] (입력/옵션 유지한 채 복귀 — 사용자가 값을 다시 입력하지 않게 함)

[G-3 결과 화면]에서:
   - [출력 폴더 열기] → OS 파일탐색기 실행(로컬 파일시스템 호출, API 아님)
   - [새 파일 변환] → [G-1 메인 화면: 빈 상태]로 복귀
   - 후원 버튼(REQ-025) 상시 노출(§1-1-b)

[언제든] 메뉴/버튼 → [G-6 정보(About) 화면] (라이선스 MIT, 지원 HWPX 버전, 후원 링크, GitHub 저장소 링크)
[언제든] 메뉴/버튼 → [G-7 설정 화면] (최근 변환 목록 + "목록 지우기", OCR 기본 언어)
[예상치 못한 예외] 어느 화면에서든 → [G-5 크래시 다이얼로그] (03 §7-2, sys.excepthook)
```

**(a) 출력 파일 존재 사전 감지 — API 확장 아님**: `ConversionOptions.overwrite_existing`은 이미 03 §4-1에 정의된 값이다. GUI가 출력 경로 확정 시점에 `Path.exists()`로 미리 확인해 사용자에게 즉시 알려주는 것은 로컬 파일시스템에 대한 클라이언트 자체 점검(표준 라이브러리 수준)이며, orchestrator에 새 API를 요구하지 않는다. 단, 이 사전 점검과 실제 저장 시점 사이에 파일이 생성되는 경쟁 상태(race condition)가 있을 수 있어, `OutputPathError`(엣지케이스: 출력충돌)는 여전히 최종 방어선으로 G-4에 남는다.

**(b) 후원 버튼 상시 노출 — REQ-025/unit-18**: 결제 로직 없이 `webbrowser.open(SPONSOR_URL)`만 호출한다(03 §4-4). 클릭 이벤트를 로컬/원격 어디에도 기록하지 않는다(03 §6-2).

### 1-2. CLI 플로우 (REQ-013, P1~P4 중 CLI 선호/스크립팅 사용자)

```
$ pdftohwpx convert input.pdf [-o output.hwpx] [--ocr] [--lang kor+eng] [--overwrite] [--verbose]
   │
   ├─ 인자 오류(예: 파일 미지정) ──────→ [C-3 사용법(--help) 출력] + 종료코드 2
   │
   ▼ 정상 인자
[C-1 단일 변환: 진행 표시]
   - ProgressEvent를 1줄 캐리지리턴(\r) 갱신 텍스트 진행바로 렌더링(03 §4-3)
   - loading 단계 message에 대용량 경고가 있으면 진행바 갱신 전에 그 줄을 먼저 별도 출력(캐리지리턴으로 덮어쓰지 않음 — 사용자가 놓치지 않도록)
   ▼ convert() 반환
   ├─[success] ─────→ [C-1 요약 출력] "[OK] input.pdf -> output.hwpx (경고 N건)" + 종료코드 0(경고 없음) / 1(경고 있음)
   └─[실패] ────────→ [C-1의 에러 상태] stderr에 오류 메시지, 종료코드 2 (§2 C-1/C-2 참고, 별도 화면번호 없음)
   ▼ (모든 경우 공통, 배치가 아닌 단일 실행 종료 시 1회)
[후원 안내 1줄] "이 도구가 유용했다면 GitHub Sponsors에서 후원해주세요: {SPONSOR_URL}"

$ pdftohwpx batch input_dir/ [-o output_dir/] [--ocr] [--lang kor+eng] [--overwrite]
   │
   ├─ input_dir에 PDF가 0개 ──────→ [C-2 빈 상태 출력] "변환할 PDF 파일이 없습니다: input_dir/" + 종료코드 1(경고 성격, 실패는 아님)
   ▼ PDF N개 발견
[C-2 배치 진행: 파일별 순차 처리]
   - 파일마다 "[N/M] input.pdf 처리 중..." 진행 표시 → 완료 시 그 줄을 "[OK]"/"[WARN]"/"[FAIL]" 결과 줄로 교체
   - 한 파일의 실패가 나머지 파일 처리를 막지 않음(03 §5 격리 원칙)
   ▼ 전체 완료
[C-2 배치 요약] "총 M개 중 성공 X / 경고 Y / 실패 Z" + 종료코드(하나라도 실패 시 2, 전부 경고 이하만 있으면 1, 전부 완전성공 0)
[후원 안내 1줄] (배치당 1회만 출력, 파일마다 반복하지 않음 — 노이즈 방지)
```

**--verbose 옵션**: 위 모든 흐름에 로그 레벨 DEBUG 상세 출력이 추가된다(03 §7-1). 기본 모드에서 숨겨지는 전체 파일 경로도 `--verbose`에서만 노출된다(03 §6-2 원칙과 정합 — 사용자가 명시적으로 요청했을 때만).

## 2. 화면별 명세

> 표기 규칙: "정상/빈/에러/로딩" 4개 상태를 화면마다 명시한다. 해당 없는 상태는 "해당 없음(사유)"로 명시한다(누락과 구분하기 위함).

### G-1. 메인 화면 (`gui/app.py`, REQ-015)

- **목적**: 변환할 PDF 파일과 옵션을 선택하고 변환을 시작한다.
- **구성 요소**:
  - 입력 파일 경로 표시 필드(읽기 전용 텍스트) + "찾아보기…" 버튼(`filedialog.askopenfilename`, filter `*.pdf`)
  - 출력 파일 경로 표시 필드(편집 가능, 기본값 자동 생성) + "다른 위치에 저장…" 버튼(`filedialog.asksaveasfilename`)
  - "덮어쓰기 허용" 체크박스(`ConversionOptions.overwrite_existing`) — 출력 경로 사전 감지(§1-1-a)로 충돌 시 자동 강조
  - "OCR로 스캔본 인식" 체크박스(`ConversionOptions.enable_ocr`) → 체크 시 "한국어"/"영어" 언어 체크박스 노출(최소 1개 선택 강제, 문자열로 합성해 `ocr_lang`에 전달, 예: 둘 다 체크 시 `"kor+eng"`)
  - [변환 시작] 기본 액션 버튼
  - 하단 고정 바: 후원 버튼(REQ-025), 정보(About) 버튼, 설정 버튼
- **상태**:
  - **빈 상태**: 앱 최초 실행 또는 "새 파일 변환" 복귀 시. 입력/출력 필드 플레이스홀더("PDF 파일을 선택하세요"), [변환 시작] 버튼 비활성화(회색), OCR 체크박스 기본 OFF.
  - **정상 상태(파일 선택됨)**: 위 §1-1 플로우 참고. [변환 시작] 활성화.
  - **에러 상태(인라인)**: 출력 파일 존재 감지 시 인라인 경고 배지("⚠ 같은 이름의 파일이 이미 있습니다") — 모달이 아니라 화면 내 인라인 표시(사전 감지이므로 차단하지 않고 안내만 함, 덮어쓰기 체크 시 배지 사라짐). OCR 언어를 하나도 선택하지 않고 OCR 체크박스만 켠 경우 [변환 시작] 비활성화 + 툴팁("언어를 1개 이상 선택하세요").
  - **로딩 상태**: 해당 없음 — 이 화면 자체는 즉시 렌더링되며, 변환 시작 클릭 즉시 G-2로 전환되므로 G-1 내부에 로딩 스피너가 없다.

### G-2. 진행 화면 (변환 진행 중, `gui/app.py` + `threading.Thread`)

- **목적**: `ProgressEvent` 스트림을 사용자에게 실시간으로 보여주고, 변환이 끝나면 자동으로 G-3/G-4로 전환한다.
- **구성 요소**: 결정적(determinate) 진행바(0~100%, `current_page/total_pages`로 계산), 단계 라벨("PDF 읽는 중…"/"내용 추출 중…"/"HWPX 문서 작성 중…"/"저장 중…"/"완료"; `ProgressEvent.stage`를 한국어로 매핑), 페이지 카운터("3 / 10 페이지"), 취소 버튼 **없음**(03 §8-1 항목 5, YAGNI로 명시적 배제 — 화면에 취소 버튼을 만들지 않는 것 자체가 의도된 설계).
- **상태**:
  - **로딩 상태(=이 화면의 기본 상태)**: 위 구성 요소가 `ProgressEvent`마다 갱신됨. `total_pages`를 아직 모르는 초기 `loading` 단계에서는 진행바를 비결정적(indeterminate, 좌우 왕복 바)으로 표시하다가 `total_pages`가 확정되는 즉시 결정적 모드로 전환한다(0페이지 PDF라 `total_pages=0`인 극단 케이스는 즉시 G-4 오류로 전환되므로 이 화면에 오래 머물지 않음).
  - **엣지케이스(대용량 PDF)**: `loading` 단계 `message`에 대용량 경고 문구가 포함되면 진행바 위에 별도 배너("⏱ 대용량 파일입니다. 처리 시간이 길어질 수 있습니다")를 표시하고, 배너는 사용자가 닫기 전까지 유지(진행률 갱신과 별개 레이어).
  - **정상/빈/에러 상태**: 해당 없음 — 이 화면은 순수 전이(transient) 화면이며 종료 즉시 G-3 또는 G-4로 자동 전환된다. 단, "창 닫기 시도" 인터랙션만은 이 화면 고유의 확인 다이얼로그(§1-1)로 존재한다.

### G-3. 결과 화면 (변환 완료, `ConversionResult` 소비)

- **목적**: 변환 통계와 경고(품질 리포트, REQ-016)를 보여주고 후속 행동(폴더 열기/새 변환)을 제공한다.
- **구성 요소**:
  - 상단 배지: 완전 성공("✓ 변환 완료") / 부분 성공("⚠ 경고 N건과 함께 완료")
  - 통계 요약(`ConversionStats` 전 필드 매핑): "총 {total_pages}페이지 · 표 {tables_preserved_fully}/{tables_detected}개 완전 보존 · 이미지 {images_embedded}개 삽입 · 대체문자 {chars_replaced_with_placeholder}자 · 처리시간 {elapsed_seconds:.1f}초"
  - 경고 목록(`ConversionResult.warnings`, 있을 때만): 항목당 아이콘(코드 접두사로 분류: `TABLE_*`→표 아이콘, `TOUNICODE_*`→글자 아이콘, `FORMULA_*`→수식 아이콘, `PAGE_SKIPPED`→페이지 아이콘, `LARGE_FILE_SLOW`→시계 아이콘) + `detail` 문구(이미 한국어 완성 문장, 03 §4-1 주석에 따라 그대로 노출)
  - [출력 폴더 열기] 버튼, [새 파일 변환] 버튼, 후원 버튼(상시)
- **상태**:
  - **정상 상태(완전 성공)**: `warnings=[]`. "경고 없음 — 모든 요소가 정상적으로 변환되었습니다" 문구로 명시적 빈 목록을 표시(목록을 그냥 숨기지 않고, "문제 없음"을 적극적으로 알려 사용자가 불확실해하지 않게 함).
  - **빈 상태**: 위와 동일(경고 0건 = 목록의 빈 상태). 별도 빈 상태 없음.
  - **에러 상태**: 해당 없음 — `success=False`는 이 화면이 아니라 G-4로 라우팅된다(이 화면은 `success=True`일 때만 진입).
  - **로딩 상태**: 해당 없음(전이 완료 후 화면).
  - **엣지케이스 매핑**: 수식 판정 불가(`FORMULA_FALLBACK_IMAGE`) → 이 화면의 경고 목록 항목으로 정상 노출(오류 아님, §0 확인).

### G-4. 오류 다이얼로그 (모달, `ConversionResult.errors` 소비 — 03 §4-2 예외 계층)

- **목적**: 변환이 시작조차 되지 않았거나 중간에 실패했을 때, 원인과 다음 행동을 명확히 안내한다.

- **코드별 문구/액션 매핑(03 §4-2 예외 계층 7종 전부 + 계층 밖 캐치올 1종 — 03 원문 그대로 승계하되, 03이 사용자 문구를 비워둔 2곳은 04단계에서 UX 카피로 보완)**:

  - **키보드 인터랙션**: Enter=주 액션 버튼 실행, Esc=[확인]과 동일(다이얼로그 닫고 G-1 복귀).

### G-5. 크래시 다이얼로그 (`sys.excepthook`, 03 §7-2 — `orchestrator.convert()` 바깥에서 발생한 未처리 예외)

- **목적**: GUI 이벤트 루프 자체의 버그 등, `convert()`가 잡아내지 못하는 진짜 미처리 예외를 최후 방어선에서 사용자에게 안내한다.
- **구성 요소**: "예상치 못한 오류가 발생했습니다" 제목, [로그 폴더 열기] 버튼, [GitHub Issue 등록하기] 버튼(브라우저로 이슈 등록 페이지 열기, `webbrowser.open`), [종료] 버튼.
- **상태**: **에러 상태만 존재**(정상/빈/로딩 해당 없음). 자동 전송은 하지 않는다(03 §7-2, 사용자가 직접 첨부).
- **G-4와의 구분(구현자를 위한 명시)**: G-4는 `ConversionResult.errors`로 정상 반환된 "처리된 실패"이고, G-5는 그 반환 경로 자체가 무너진 "미처리 예외"다. 두 화면의 문구를 비슷하게 통일했지만 트리거 지점이 다르므로 구현 시 반드시 별도 컴포넌트/이벤트 핸들러로 구현한다(혼동 방지를 위해 명시).

### G-6. 정보(About) 화면 (REQ-025, REQ-012, 03 §8-3)

- **목적**: 라이선스, 버전, 후원 링크, 지원 범위를 한 곳에 모은다.
- **구성 요소**:
  - 앱 이름 + 버전 번호
  - 라이선스: "MIT License" 고정 텍스트(DEC-014 확정) + [LICENSE 전문 보기] 버튼(unit-10 산출물 파일을 텍스트 뷰어로 표시)
  - 지원 HWPX 버전: "지원 버전: `{HWPX_MIN_SUPPORTED_VERSION}`" — **자리표시자**(03 §8-3 항목 3, 05/06단계 실측 전까지 상수값 자체가 미정이므로 화면도 그 값을 그대로 렌더링하면 됨. 화면 설계 자체에 추가 조치 불필요)
  - 후원 섹션: "이 프로그램이 마음에 드셨다면 GitHub Sponsors로 후원해주세요" + 버튼(`webbrowser.open(SPONSOR_URL)`) — **URL 자리표시자**(03 §8-3 항목 2, 05단계 unit-18에서 실제 URL 확정)
  - GitHub 저장소 링크(오픈소스 공개, DEC-006)
  - 서드파티 라이선스 고지 링크([THIRD_PARTY_LICENSES.md 보기], unit-10)
- **상태**: 정적 정보 화면이라 **정상 상태만 존재**(빈/에러/로딩 해당 없음 — 모든 필드가 앱 실행 시점에 상수/파일에서 즉시 로드 가능).

### G-7. 설정 화면 (03 §6-2 "최근 목록 지우기" 권고 반영, `settings.json` 소비)

- **목적**: 개인정보 성격을 가질 수 있는 "최근 변환 파일 목록"(03 §3-2)을 사용자가 직접 관리하게 한다.
- **구성 요소**:
  - 최근 변환 파일 목록(경로 문자열, 최대 10개, `settings.json` 스키마 그대로)
  - [목록 지우기] 버튼 → 클릭 시 확인 다이얼로그("최근 목록을 모두 지우시겠습니까?") → 확인 시 `settings.json`의 해당 필드를 즉시 비움
  - OCR 기본 언어 설정(마지막 사용값을 다음 실행에 기본값으로 반영 — `settings.json`의 "마지막 사용 OCR 언어" 필드와 1:1 대응)
- **상태**:
  - **빈 상태**: 최근 변환 기록이 없을 때 — "아직 변환 기록이 없습니다" 문구, [목록 지우기] 버튼 비활성화.
  - **정상 상태**: 최근 목록 최대 10개 표시(최신순).
  - **에러 상태**: 해당 없음(파일 시스템 쓰기 실패 시에도 조용히 무시하고 다음 실행에서 기본값 재생성 — 03 §3-2 "삭제하면 기본값으로 재생성"과 일관되게, 설정 저장 실패가 사용자 작업을 막지 않도록 설계).
  - **로딩 상태**: 해당 없음(로컬 JSON 파일 읽기는 사실상 즉시 완료됨).

### C-1/C-2. CLI 출력 "화면"(터미널 텍스트, `cli/__main__.py`)

- **목적**: GUI 없이 스크립트/배치 환경에서 변환을 수행하고 결과를 텍스트로 전달한다.
- **구성 요소**: 진행률 텍스트 줄(`\r` 갱신), 파일별 요약 줄(`[OK]`/`[WARN]`/`[FAIL]` 접두사 — WARN은 03 §4-3에 명시된 "종료코드 1(경고 존재)" 상태를 시각적으로 구분하기 위해 04단계에서 추가한 표기 규칙), 배치 합계 줄, 후원 안내 1줄, `--verbose` 시 상세 로그.
- **상태**:
  - **정상 상태**: `[OK] a.pdf -> a.hwpx (경고 0건)`, 종료코드 0.
  - **빈 상태**: `batch` 대상 디렉터리에 PDF가 0개 — "변환할 PDF 파일이 없습니다: {input_dir}", 종료코드 1(실패는 아니지만 성공도 아님을 구분).
  - **에러 상태**: stderr에 오류 메시지(G-4 표와 동일 문구 재사용, 터미널이므로 모달 대신 텍스트) + 종료코드 2. `batch`에서 개별 파일 실패는 `[FAIL] c.pdf: {메시지}`로 표시하고 나머지 파일 처리를 계속한다(격리 원칙).
  - **로딩 상태**: 진행 중인 파일의 `\r` 갱신 줄(캐리지리턴으로 같은 줄 덮어쓰기). 터미널이 캐리지리턴을 지원하지 않는 환경(파이프로 리다이렉트된 경우 등)에서는 자동으로 매 `ProgressEvent`를 새 줄로 출력하도록 폴백한다(`sys.stdout.isatty()` 확인 — 구현자를 위한 명시).

### C-3. CLI `--help` (`argparse` 기본 제공)

- **목적**: 사용법을 즉시 확인.
- **상태**: **정상 상태만 존재**(정적 텍스트). `pdftohwpx`, `pdftohwpx convert -h`, `pdftohwpx batch -h` 3단계 도움말 계층(argparse subparser 표준 동작).

| `color-focus-ring` | `#1F6FEB` (2px solid) | 키보드 포커스 표시 | 배경(`#FFFFFF`)과 3:1 이상 확보(비텍스트 대비 기준, WCAG 1.4.11) |
| `color-border` | `#D0D3D9` | 입력 필드/구분선 | 비텍스트 요소 3:1 목표(테두리는 장식이 아니라 입력 필드 경계를 나타내는 기능적 요소이므로) |

- **원칙**: 상태(성공/경고/오류)는 **색상만으로 구분하지 않는다** — 항상 아이콘 + 텍스트 라벨을 함께 표기한다(색맹 사용자 대응, WCAG 1.4.1). 예: 경고는 "⚠" 아이콘 + "경고" 텍스트 + 주황 계열 색, 성공은 "✓" 아이콘 + "완료" 텍스트 + 초록 계열 색.
- 실제 렌더링 시 OS별 폰트 안티앨리어싱/색 프로파일 차이가 있을 수 있어, 05/06단계 구현 시 실제 스크린샷으로 대비를 재측정하는 것을 권고한다(설계 단계 계산값은 sRGB 기준 이론치).

### 3-2. 타이포그래피

| 토큰명 | 폰트 | 크기 | 용도 |
|---|---|---|---|
| `font-heading` | 맑은 고딕(Malgun Gothic, Windows 기본 한글 폰트) Bold | 13pt | 화면 제목("변환 완료", "오류" 등) |
| `font-body` | 맑은 고딕 Regular | 10pt | 본문, 버튼 라벨 |
| `font-caption` | 맑은 고딕 Regular | 9pt | 보조 설명, 통계 캡션 |
| `font-mono` | Consolas | 9pt | 파일 경로, 로그, CLI 출력 |

- 시스템 폰트가 없는 환경(비Windows) 폴백: `font-heading`/`font-body`/`font-caption`은 Tk 기본 `TkDefaultFont` 계열로 자동 대체, `font-mono`는 `TkFixedFont`로 대체(크로스플랫폼 실행 가능성을 열어둔 03 §2-1 방침과 일관).
- 최소 본문 크기 10pt 이하로 내려가지 않는다(저시력 사용자 가독성, §5-2 접근성과 연결). 사용자가 OS 텍스트 크기 설정을 키운 경우 Tkinter는 자동 반영되지 않으므로, §6에서 별도 대응을 정의한다.

### 3-3. 간격/레이아웃 그리드

- 기준 단위 4px. 사용 값: 4 / 8 / 12 / 16 / 24 / 32(px).
- 화면 좌우 여백 16px, 구성 요소 간 세로 간격 12px, 버튼 그룹 내부 간격 8px, 섹션 간 간격 24px.
- 버튼 최소 크기: 높이 32px × 폭 88px(마우스 클릭 정확도 및 운동 능력 저하 사용자 배려 — WCAG 2.1 AA 자체는 데스크톱 포인터 타깃 크기를 규정하지 않지만, 실무 기준으로 04단계가 최소값을 못박아 "너무 작아 못 누르는" 실패를 예방한다).

### 3-4. 아이콘

- 시스템 아이콘 폰트에 의존하지 않고(Tkinter 기본 이모지/유니코드 글리프 렌더링이 OS마다 다를 수 있음), 필요한 아이콘(✓ 성공, ⚠ 경고, ✕ 오류, ⏱ 대용량, 📁 폴더, 📄 파일)은 **텍스트 유니코드 글리프 + 항상 병기되는 텍스트 라벨**로 구성한다(아이콘만으로 의미를 전달하지 않음 — 스크린리더가 유니코드 글리프를 못 읽거나 이상하게 읽는 경우를 텍스트 라벨이 보완).

## 5. 접근성 기준 (데스크톱 Tkinter 앱, WCAG 2.1 AA 목표로 재해석)

> "웹이 아니므로 해당 없음"으로 넘기지 않는다. 데스크톱 앱도 (a) 키보드만으로 완전 조작 가능해야 하고, (b) 색 대비를 지켜야 하며, (c) 플랫폼 접근성 API(Windows UI Automation/MSAA, macOS Accessibility API)를 통해 스크린리더가 UI를 읽을 수 있어야 한다는 원칙은 동일하게 적용된다.

### 5-1. 키보드 내비게이션 (WCAG 2.1.1/2.1.2 상당)

- 모든 화면의 모든 인터랙티브 요소(버튼, 체크박스, 텍스트 필드, 리스트)는 **마우스 없이 Tab/Shift+Tab만으로 도달 가능**해야 한다. Tab 순서는 화면의 논리적 흐름(위→아래, 왼쪽→오른쪽)과 일치시킨다(예: G-1은 입력경로→찾아보기→출력경로→다른위치저장→덮어쓰기 체크박스→OCR 체크박스→언어 체크박스→변환시작→하단바 순).
- 모든 버튼은 Enter/Space로 활성화된다.
- 모달(G-4/G-5)이 열리면 포커스가 즉시 모달 내부로 이동하고(포커스 트랩), 모달이 닫히기 전까지 Tab이 모달 밖 요소로 빠져나가지 않는다. 닫히면 포커스는 모달을 연 요소로 복귀한다.
- Esc 키는 모든 모달을 닫는 보편 단축키로 통일한다.
- 자주 쓰는 액션에 니모닉(Alt+밑줄 글자)을 부여한다: [변환 시작](Alt+S), [찾아보기](Alt+B), [출력 폴더 열기](Alt+O) 등 — Tkinter `underline` 인덱스 옵션으로 구현.
- 진행 화면(G-2)에서도 창 닫기(Alt+F4 포함)는 반드시 확인 다이얼로그를 거치도록 하여, 키보드로만 조작하는 사용자가 실수로 진행 중인 작업을 잃지 않게 한다.

### 5-2. 색 대비 (WCAG 1.4.3/1.4.11)

- §3-1에서 정의한 텍스트 대비 4.5:1 이상(본문), 비텍스트 UI 요소(포커스 링, 입력 필드 테두리) 대비 3:1 이상을 모든 화면에 적용한다.
- 상태 표시는 색상 단독으로 하지 않고 아이콘+텍스트를 병기한다(§3-4).
- 다크 모드는 v1 범위에 포함하지 않는다(REQ-015가 요구하지 않음, YAGNI) — 단, OS가 강제로 다크 테마를 적용해도 Tkinter 커스텀 `ttk.Style`이 §3-1 토큰을 강제하므로 저대비로 깨지지 않는다(라이트 테마 고정, 03의 Tkinter 채택 트레이드오프에 따른 04단계 대응).

### 5-3. 스크린리더/플랫폼 접근성 API (WCAG 4.1.2 상당) — 알려진 한계와 구체적 완화책

- **알려진 한계(정직하게 명시)**: Tkinter 기본 위젯은 자체 렌더링 방식(대부분 네이티브 OS 컨트롤이 아님)을 사용해, Qt/WinForms 앱 대비 Windows UI Automation 노출 수준이 낮다. 이는 "접근성 기준 생략"이 아니라 **선택한 GUI 툴킷(DEC-009)의 실제 제약**이며, 03 §8-1 항목 3이 4단계에 인수인계한 사항이다.
- **완화책 1 — ttk 위젯 우선 사용**: 순수 `tk.*` 위젯 대신 `ttk.*` 위젯(테마 지원 위젯)을 사용한다. `ttk` 위젯은 내부적으로 플랫폼 네이티브 렌더링에 더 가깝게 동작해 접근성 브리지 호환성이 상대적으로 낫다.
- **완화책 2 — 명시적 그룹/라벨 구조**: 개별 `Label`을 입력 필드 옆에 배치하는 데 그치지 않고, 관련 위젯을 `ttk.LabelFrame(text=...)`으로 묶어 스크린리더가 그룹명을 함께 읽게 한다(예: "OCR 옵션" LabelFrame 안에 체크박스 2개).
- **완화책 3 — 상태 변경의 텍스트화**: 진행률처럼 시각적으로만 바뀌는 정보(진행바 채워짐 정도)는 반드시 인접한 텍스트 라벨(예: "3/10페이지 처리 중")로도 동시에 갱신한다 — 스크린리더가 그래픽 진행바 자체를 못 읽어도 텍스트 갱신은 포커스가 그 라벨에 있을 때 읽을 수 있다.
- **완화책 4 — CLI를 1급 접근성 대안으로 문서화**: CLI(`cli/__main__.py`)는 순수 텍스트 입출력이라 스크린리더 호환성이 GUI보다 원천적으로 높다. README(unit-10/11)에 "스크린리더 사용자는 CLI 사용을 권장합니다"를 명시적으로 안내한다 — 이는 회피가 아니라, 두 인터페이스(GUI/CLI)가 이미 공존하는 이 프로젝트의 구조적 장점을 접근성 관점에서 적극적으로 활용하는 것이다.
- **검증 기준(10단계 인수인계 사항)**: Windows 내레이터(Narrator) 및 NVDA로 G-1~G-7 전 화면의 핵심 조작(파일 선택→변환→결과 확인)이 최소한 "포커스된 위젯의 종류와 라벨"은 읽히는지 실기기 테스트를 06/09단계에서 수행할 것을 권고한다(자동화된 정적 분석만으로는 Tkinter 접근성 트리 문제를 완전히 잡아낼 수 없음).

### 5-4. 기타 AA 상당 기준

- **타이밍(WCAG 2.2.1)**: 모든 다이얼로그와 배너는 자동으로 사라지지 않는다(사용자가 직접 닫기 전까지 유지) — 저시력/인지 장애 사용자가 읽을 시간을 충분히 확보.
- **오류 식별(WCAG 3.3.1)**: 모든 오류는 무엇이 문제인지 텍스트로 구체적으로 설명하고(§2 G-4 표), 어떻게 해결할지 액션 버튼을 함께 제공한다.
- **터치/클릭 타깃 크기**: §3-3에서 정의한 최소 32×88px을 모든 클릭 가능 요소에 적용.
- **포커스 가시성(WCAG 2.4.7)**: Tkinter 기본 포커스 표시(점선 테두리)를 임의로 제거하지 않으며, §3-1 `color-focus-ring` 토큰으로 커스텀 위젯에도 동일 수준의 포커스 표시를 강제한다.

## 6. 반응형/디바이스 대응 기준

> 모바일 브레이크포인트 개념은 이 프로젝트에 적용되지 않는다(데스크톱 전용, REQ-015). 대신 데스크톱 환경의 실제 변수(창 크기, 고해상도/DPI, 멀티모니터, 터미널 폭, OS)에 대응한다.

### 6-1. 창 크기/레이아웃

- 최소 창 크기 480×360px(`wm_minsize`)로 고정 — 이보다 작아지면 위젯이 겹치거나 잘리는 것을 방지.
- `grid` 레이아웃의 행/열 `weight`를 지정해 창을 키우면 여백이 비례해서 늘어나고(리스트 영역이 세로로 확장), 텍스트 필드는 가로로 확장되도록 한다.
- G-3 경고 목록처럼 항목 수가 가변적인 영역은 스크롤 가능한 컨테이너(`ttk.Treeview` + 스크롤바)로 구성해, 항목이 많아도 창 크기와 무관하게 전체 접근이 가능하게 한다.
- 창을 마지막 사용 크기로 복원한다(`settings.json`의 "GUI 창 크기" 필드, 03 §3-2에 이미 정의된 값을 그대로 소비 — 새 데이터 요구 아님).

### 6-2. 고해상도(High-DPI)/멀티 모니터

- 앱 시작 시(Tk 루트 생성 전) Windows에서 `ctypes.windll.shcore.SetProcessDpiAwareness(1)` 호출로 시스템 DPI 인식을 활성화한다 — 하지 않으면 고해상도 모니터에서 텍스트/위젯이 흐릿하게 렌더링된다(1차 배포 타깃이 Windows, DEC-011).
- Tk의 `tk scaling` 값을 OS DPI 배율에 맞춰 조정해 §3-2 폰트 크기(pt 단위)가 실제로 일관된 크기로 보이게 한다.
- 창은 마지막으로 종료된 모니터/위치에 복원하되, 그 모니터가 더 이상 연결되어 있지 않으면(멀티모니터 구성 변경) 주 모니터 중앙에 배치하는 폴백을 둔다.

### 6-3. OS 텍스트 크기 설정 대응

- Tkinter는 OS 접근성 설정(예: Windows "텍스트 크기 확대")을 자동으로 반영하지 않는 한계가 있다 — 이를 완화하기 위해 G-7 설정 화면에 "글자 크기: 보통/크게" 2단계 옵션을 제공해(§3-2 `font-body` 10pt ↔ 13pt 전환), 저시력 사용자가 OS 설정과 별개로 앱 내에서 직접 조정할 수 있게 한다(신규 데이터 아님 — 순수 클라이언트 렌더링 옵션이며 `settings.json`에 저장 가능한 로컬 환경설정 값으로, 03 §3-2 "설정/이력 저장" 원칙과 일관).

### 6-4. 플랫폼 차이 (Windows 우선, DEC-011)

- v1 패키징은 Windows 전용(DEC-011)이므로 위 DPI 대응은 Windows 기준으로 구체화했다. macOS/Linux는 소스 실행만 지원되며(03 §8-1 항목 7), 해당 환경에서는 OS 기본 DPI 처리에 위임하고 04단계에서 별도 미세조정은 하지 않는다(범위 밖, 향후 패키징 확장 시 재검토).
- OS 네이티브 파일 다이얼로그(`filedialog`)를 그대로 사용해, 파일 선택 경험 자체는 OS 표준과 자동으로 일치시킨다(별도 커스텀 다이얼로그를 만들지 않음 — 과설계 배제 원칙과도 일치).

### 6-5. CLI의 "반응형" — 터미널 크기 대응

- 진행률 줄 길이를 `shutil.get_terminal_size()`로 확인한 터미널 폭에 맞춰 잘라내거나 줄바꿈 없이 한 줄로 유지한다. 폭을 가져올 수 없는 환경(파이프/리다이렉트)에서는 고정 폭 80컬럼을 기본값으로 가정한다.
- 출력이 파일로 리다이렉트되거나 파이프로 연결된 경우(`sys.stdout.isatty() == False`) `\r` 캐리지리턴 갱신을 비활성화하고 매 이벤트를 새 줄로 출력한다(§2 C-1/C-2에 이미 명시).
