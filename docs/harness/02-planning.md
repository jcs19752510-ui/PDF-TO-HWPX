## 1. 서비스/기능 개요 및 목적

**PDF-TO-HWPX**는 개인 사용자가 로컬 환경에서 PDF 문서를 한글과컴퓨터의 개방형 문서 포맷인 HWPX(OWPML, KS X 6101)로 변환할 수 있게 하는 범용 변환 도구다.

- **목적**: (a) 2026년 진행 중인 정부의 공공문서 HWP→HWPX 전환 정책(01보고서 2-1절)으로 개인이 관공서·학교 제출용 문서를 HWPX로 다뤄야 하는 실질 수요가 생기고 있으나, (b) 기존 경쟁 서비스(한PDF/알PDF/HiPDF/폴라리스오피스, 01보고서 3절)는 "로컬 처리 + 무료 + 개인용 사용성"을 모두 갖춘 경우가 드물다는 시장 공백을 메운다.
- **핵심 동작**: 사용자가 로컬 PC에 있는 PDF 파일을 지정하면, 문서를 파싱해 텍스트/이미지/표 구조를 최대한 보존한 HWPX 파일로 로컬에 저장한다. 문서 내용을 요약·해석·추천하지 않고 표현 형식만 옮기는 기계적 변환에 한정한다(01보고서 5-1절 규제 판단의 근거와 동일 선상).
- **비목적(명시적으로 하지 않는 것)**: 문서 내용에 대한 의미적 판단(요약/추천/자동 검토), 서버로의 원문 전송을 전제로 한 협업·공유 기능. (근거는 4·8절에서 상술)

## 2. 타깃 사용자 및 페르소나

01보고서 4절("타깃 사용자층의 최근 행동 변화/니즈")에서 도출된, 근거가 확인된 페르소나만 채택한다(근거 없는 페르소나는 추가하지 않음 — 필수 원칙).

| 페르소나 | 상황 | 근거(01보고서) |
|---|---|---|
| **P1. 관공서/학교 제출자** | 관공서·학교가 배포한 PDF 서식을 받아, 이를 한글 문서로 채우거나 재편집해서 제출해야 함 | 2-2, 4절 — "관공서 서식, PDF를 HWP로 수정·제출" 니즈 |
| **P2. 스캔본 재활용자** | 계약서·오래된 문서 등 스캔된 이미지 PDF를 편집 가능한 한글 문서로 되살려야 함 | 2-2절 — HiPDF 등의 OCR 변환 용도 설명 |
| **P3. 한글 프로그램 미보유자** | 한글 프로그램이 없거나 구버전이라 PDF로 받은 문서를 편집할 수 없음 | 2-2절 — 정부 '공공 한글' 무료 배포 정책이 겨냥하는 것과 동일 페르소나 |
| **P4. 프라이버시 민감 사용자** | 계약서·이력서·스캔 신분서류 등 개인정보가 담긴 문서를 외부 서버에 올리고 싶어하지 않음 | 4절 — 알PDF/폴라리스오피스의 "로컬 처리" 마케팅이 시사하는 니즈 |

- **채택하지 않은 후보**: "한컴오피스 고급 사용자"(수식·복잡 표 전문 편집자)는 6절 도메인 운영 규칙상 수식/복잡 표 변환이 구조적으로 불완전할 수밖에 없어(01보고서 6절 4·5번) 이 도구의 주 타깃으로 삼지 않는다 — 대신 "완벽 변환"이 아닌 "기본 서식 위주의 실용적 변환"을 표방한다(4절 우선순위 정책과 연결).

## 4. 기능 범위 (In-Scope / Out-of-Scope, MoSCoW)

> REQ-ID는 `docs/harness/traceability.md`와 1:1 대응한다. 배포형태와 과금모델은 v3 기준 **모두 확정**되었다(DEC-004: 배포형태=로컬 전용, DEC-005: 과금모델=후원(기부), DEC-006: 배포범위=오픈소스 공개 — 8절 참고). 아래 REQ 표의 "(잠정, Q-n)" 표기는 확정 처리되어 "(확정, DEC-00n)"으로 정리했으며, 과금모델이 "완전 무료"에서 "후원(기부)"로 확정됨에 따라 REQ-025(신규)를 추가하고 REQ-012·REQ-022를 갱신했다.

### 규칙 I·규칙 J 반영 요약 (필수 연결)

- **규칙 I**: 01보고서 5-1절은 "금융/의료/법률/보험 인허가 대상 아님"으로 잠정 판단하되, "(a) LLM 요약/해석/추천 기능 추가, (b) 특정 업종 전용 템플릿·자동 검토 기능 추가" 시 재검토가 필요하다고 조건을 달았다. 본 기획서는 (a)에 해당하는 기능을 REQ-020으로, (b)에 해당하는 기능을 REQ-023으로 **각각 Out-of-Scope 처리**함으로써 두 재검토 트리거를 모두 회피했다. 따라서 **규칙 I의 재검토 조건은 이번 v1 기획 범위 내에서는 발동하지 않는다.** 이후 단계(3~13)에서 누군가 REQ-020/023을 In-Scope로 되돌리려면, 되돌리는 시점에 반드시 규칙 I를 재적용하고 실제 법률 자문 권고 문구를 함께 등록해야 한다(8절 가정 A-6 참고).
- **규칙 J**: 01보고서 8-5절은 LLM/VLM을 서비스에 내장하면 규칙 J(프롬프트 인젝션 방어/출력 새니타이즈/도구 권한 최소화/비용 레이트리밋)가 전면 적용된다고 명시한다. 본 기획서는 LLM/VLM 레이아웃 복원 기능을 REQ-020으로 **Out-of-Scope 처리**하고, 파싱은 규칙 기반(PyMuPDF류)·OCR은 전통 방식(Tesseract류)만 사용하기로 함으로써 **규칙 J의 적용 대상에서 이번 v1 기획을 제외**했다. 따라서 규칙 J가 요구하는 4개 안전장치용 REQ-ID는 이번 traceability.md에 등록하지 않는다(등록하지 않는 것 자체가 "위 사유 기반의 의도적 결정"이며, 8단계 커버리지 체크에서 "빠뜨린 항목"이 아니라 "의도적으로 뺀 항목"으로 traceability.md에 사유와 함께 남긴다).

## 5. 성공 지표 (측정 가능한 KPI)

실사용자 트래픽이 아직 없는 신규 개인 프로젝트이므로, 1차로는 **기술 품질 지표**를 중심으로 정의하고, 배포 이후(사용자가 생기면) 사용성 지표를 추가한다. 모두 06~08단계 테스트에서 실측 가능한 형태로 정의했다.

| KPI | 정의/측정 방법 | 목표치(v1) |
|---|---|---|
| **변환 성공률** | 테스트 코퍼스(다양한 PDF 샘플 N개, 8절 가정 A-8에서 정의) 중 크래시/미처리 예외 없이 HWPX 파일이 생성되는 비율 | ≥ 95% (수식·심각한 손상 PDF 등 알려진 한계 케이스는 "정상적으로 실패 안내"까지 포함하면 100% 목표) |

## 6. 제약 조건 (기술/일정/예산/기존 시스템 호환성)

- **기존 시스템 호환성**: 0절 스캔 결과 기존 소스코드가 없으므로 **호환성 제약 없음(신규 프로젝트)**. 단, 이 하네스(`ORCHESTRATOR.md` 규칙 A~K)와 `docs/harness/` 산출물 체계는 준수해야 한다.
- **기술적 제약**:
  - 생성 HWPX는 OWPML(KS X 6101) 스펙을 따라야 하며, 한컴의 사양 문서(revision 1.2)는 "열람은 자유, 무수정 재배포만 제한, 2차 저작물(파서/변환기) 제작은 자유"라는 조건이 확인되었으므로 사양 문서 자체를 프로젝트에 원문 그대로 재배포하지 않는다(01보고서 5-4절).
  - "스펙에 맞는 XML"만으로는 부족하다 — 특정 크기/개체 조합에서만 드러나는 세로 위치 오차(01보고서 6-6)와, 한컴오피스의 암묵적 검증 규칙까지 맞추지 않으면 경고창이 뜨거나 텍스트가 겹치는 문제(01보고서 6-8)가 보고된 바 있어, REQ-008(HWPX 출력 호환 버전 명시·준수)의 검증 범위에 이 두 항목을 반드시 포함해야 한다. 일반적인 경계값 테스트(최대/최소 크기)로는 발견되지 않는 "특정 조합"에서만 나타나는 결함이므로, 6단계 테스트 설계 시 8절 가정 A-13(테스트 코퍼스 커버리지)에서 이 두 항목을 별도로 다뤄야 한다.
  - REQ-011(로컬 처리 원칙, 확정 — Q-1=DEC-004)에 따라 외부 네트워크 호출 없이 동작하는 것을 기본 전제로 설계해야 한다(OCR·파싱 라이브러리도 로컬 실행형만 채택).
  - 01보고서 기술축에서 이름이 확인된 후보 라이브러리(`python-hwpx`, `hwpxlib`, PyMuPDF/pdfplumber류 PDF 파서, Tesseract/PaddleOCR)는 README 수준만 확인되었고 실제 성숙도(표/이미지/복잡 서식 지원 수준)는 검증되지 않았다 — **구체적 언어/스택/라이브러리 확정은 3단계 설계에서 수행**한다(ORCHESTRATOR.md 규칙 A-3 예외: 기술 스택 선택은 3단계 설계자의 권한과 책임).
- **일정 제약**: 명시적 마감일 없음(개인 프로젝트). 참고 마일스톤으로 2026년 10월 공직자통합메일 HWP 첨부 제한 시행(01보고서 2-1절)을 자체적으로 참고할 수 있으나, 이는 강제된 데드라인이 아니다.
- **예산 제약**: 유료 API(클라우드 LLM/VLM, 유료 OCR SaaS 등) 사용 금지 — REQ-020 Out-of-Scope 결정 및 로컬 처리 원칙과 정합. 오픈소스/무료 라이브러리만 사용을 전제로 기획한다(확정, Q-2=후원 모델 — DEC-005. 사용자는 결제 없이 무료로 이용할 수 있으며, 개발 단계에서 유료 클라우드 API를 쓰지 않는다는 이 제약과는 별개 사안이다).
- **법적 제약**: HWPX 사양 재배포 제한(위 기술적 제약과 동일), 저작권법 제30조(사적이용 복제) 범위를 벗어나지 않도록 로컬 처리 원칙 유지(01보고서 5-3절).

### 8-2. 확정된 질문 (사용자 응답 반영 완료 — DEC-004, DEC-005, DEC-006)

v2에서는 이 세 항목을 자체 조사로도 결정할 수 없는 비가역적 공백(치명적 공백)으로 남겨 "잠정 가정"으로 문서를 완성했었다. 이후 오케스트레이터가 사용자에게 질문해 받은 응답이 `docs/harness/decisions.md`에 DEC-004~006으로 기록되었고, v3는 이를 반영해 아래 세 항목을 모두 **확정** 처리한다. **본 문서에는 더 이상 미해결 질문이 남아있지 않다.**

- **[Q-1] 배포 형태 및 처리 위치** — **확정: (a) 로컬 전용(데스크톱/CLI)** (DEC-004)
  - (참고, v2 기록) 선택지: (a) 로컬 전용 — 개인정보 리스크 최소, 설치 필요, 서버 비용 없음 / (b) 웹 서비스 — 접근성 높음, 개인정보처리방침·보안조치 의무 발생, 서버 비용 발생 / (c) 하이브리드
  - v2의 잠정 가정(a)과 **동일한 답**이 확정되어, 본문 중 "(잠정, Q-1)" 표기만 "(확정, DEC-004)"로 정리했다(REQ-001/011/015/021, A-2/A-3/A-12). 서버 업로드가 없으므로 개인정보보호법상 개인정보처리자 지위·즉시삭제정책 의무는 발생하지 않는다(단, 향후 로컬 처리 전제가 깨지는 기능을 추가하면 재검토 필요 — DEC-004 비고).
- **[Q-2] 과금 모델** — **확정: 후원(기부) 받기** (DEC-005)
  - (참고, v2 기록) 선택지: (a) 완전 무료+오픈소스 / (b) 후원(GitHub Sponsors 등) / (c) 유료(통신판매업 신고 검토 필요)
  - v2의 잠정 가정(a) **완전 무료와는 다른 답**이 확정되었다. 결제 연동 없는 자발적 후원(후원 링크 등)이며 유료 구독/라이선스는 아니다. **실질 반영**: 신규 REQ-025(후원 링크/버튼 노출, Should-have, In-Scope)를 신설했고, REQ-022(Out-of-Scope)는 "유료 결제/구독 모델 및 실제 결제·PG 연동"으로 범위를 명확히 좁혔으며, REQ-012 비고와 §7 리스크 문구를 후원 모델 기준으로 갱신했다(A-4, §9 unit-18 신설).
- **[Q-3] 목표 배포 범위** — **확정: (b) 오픈소스 공개** (DEC-006)
  - (참고, v2 기록) 선택지: (a) 순수 개인용(비공개) / (b) 오픈소스/일반 공개
  - v2가 이미 "공개 대비 안전한 쪽"(기존 DEC-001 Tier=Standard 유지)으로 서술해둔 것과 **동일한 답**이 확정되어, 별도 REQ 신설 없이 §7 리스크 표(라이선스·특허 리스크 대응 문구)의 "(잠정)" 표기만 "(확정, DEC-006)"으로 정리했다(§5 KPI 표도 동일하게 정리). 9단계 보안검증(시크릿 노출, 의존성 CVE·라이선스)과 11단계 문서화(오픈소스 기여 가이드 등)는 공개 전제로 그대로 진행한다.
